# Manual Horizons vector acquisition — review-only

**Status:** Node.js 22+ acquisition prototype, locally tested with mocked HTTP responses. No live NASA/JPL response was retrieved in the development environment; no scientific numerical accuracy or independent source authenticity is established.

This tool adds an explicit, operator-initiated acquisition step to the independent query-plan generator in [HORIZONS_INDEPENDENT_VECTOR_PLAN.md](HORIZONS_INDEPENDENT_VECTOR_PLAN.md). It never runs in the Desktop app, never accesses user accounts, and never enables chart-ready astronomical results.

## Commands (from a full repository checkout)

```powershell
node scripts/ephemeris/prepare-horizons-vector-plan.mjs --tdb-jd 2460000.500000 --out 'D:\review\horizons-plan.json'
node scripts/ephemeris/acquire-horizons-vectors.mjs --plan 'D:\review\horizons-plan.json' --output-dir 'D:\review\responses-new'
```

The TDB Julian day above is **illustrative**. Use an epoch independently reviewed against the requested timescale. Neither this script nor the plan generator converts UTC to TDB. The output directory **must not already exist**. It is created exclusively (permissions restricted where supported) and all ten original text responses plus `response-manifest.json` are written there. On failure, cleanup removes the newly created directory **only if** it still has the original directory identity and contains exclusively unchanged files that this run recorded as its own. Unexpected, edited, substituted or symlinked entries cause cleanup to **leave the entire partial directory intact** for manual inspection; it never recursively removes unverified files. A failed acquisition can therefore leave partial files, especially on crashes or unrecognized concurrent edits.

Acquisition is **opt-in** and network access is required on the operator's computer. The script performs up to ten sequential HTTPS GETs to the exact allowlisted `https://ssd.jpl.nasa.gov/api/horizons.api` query URLs generated by the existing plan module, with 2.5 seconds between calls, 15-second request/body timeout and a 512 KiB response limit. HTTP redirects are disallowed. No API key, custom server endpoint or proxy credential is accepted from the plan. It refuses any plan that differs, even by a single field, from `buildHorizonsVectorPlan` output. Invalid plans are rejected **before** any network activity.

## Accepted response format

For each requested NAIF target, the raw text must include matching Horizons-style header values:

- Target NAIF ID; center `Solar System Barycenter (0)` and `BODY CENTER`
- Output units `KM-S`, output type `GEOMETRIC cartesian states`
- Output format `2 (position and velocity)`
- Reference frame `ICRF` or `ICRF/J2000.0` **and** coordinate system `Earth Mean Equator and Equinox of Reference Epoch` (so the ecliptic-of-J2000 output is refused)
- Start time labeled `TDB` and an unambiguous `JDTDB` column
- Exactly one row between `$$SOE` and `$$EOE`, containing the requested TDB Julian day, calendar stamp, three position components in kilometres and three velocity components in kilometres per second

The parser requires finite numeric values, rejects missing or duplicated rows, wrong target, origin, frame, units, format, and mismatched epoch. The original bytes are saved without reformatting; coordinates are never printed in CLI output. The manifest records for each target its source **claim** (if stated), original-response SHA-256 and exact query-URL SHA-256, as well as the unverified common plan epoch.

**Important:** a text file with internally consistent headers could be fabricated. `STRUCTURE_CHECKED_NOT_AUTHENTICATED` means precisely *structural and byte-integrity checks only*, never NASA/JPL cryptographic provenance or scientific accuracy. A source claim of `DE441` or `DE440` is copied as an untrusted label, not treated as a kernel audit. The raw state vectors are **solar-system-barycentric ICRF Cartesian**, and cannot be directly compared to Desktop's topocentric mean-of-date ecliptic positions. The independent scientific normalization and actual Rust parity remain separate review gates.

If the live JPL response differs from the strictly supported header layout, capture the error context privately and revise the parser **with reviewed genuine samples and regression tests**. Do not remove frame, center or time checks just to accept unrecognized output.

## Security limitations

Request bodies are bounded and malformed/oversized HTTP responses are rejected; connection retries, 30x redirects and partial-download resumptions are deliberately **not** supported. A run interrupted while writing, or an acquisition interrupted by concurrent filesystem changes, can leave a partial directory. **Inspect it manually; never assume a failed run deleted it.** The cleanup helper refuses extra files, changed metadata, symlinks, and replaced directories. Its file-identity checks reduce accidental data loss but are not atomic against an actively malicious concurrent process. Directory/file metadata checks are best effort on the local OS. Hostile concurrent filesystem replacement, authorized proxies, TLS interception, server-side dataset changes and cross-platform filesystem semantics have not been independently audited. Output paths must be in a trusted, private local folder.

## Follow-up: offline bundle integrity and pinned text API envelope

After acquisition, run:
```powershell
node scripts/ephemeris/verify-horizons-bundle.mjs --plan 'D:\\review\\horizons-plan.json' --output-dir 'D:\\review\\responses-new'
```
This offline command rechecks the ten unmodified response files, their SHA-256 values, the saved canonical query URLs and header/epoch/center/frame assumptions. See [HORIZONS_OFFLINE_BUNDLE_AUDIT.md](HORIZONS_OFFLINE_BUNDLE_AUDIT.md).

The text parser now requires the `API VERSION: 1.0` / `API SOURCE: NASA/JPL Horizons API` wire envelope shown in the official documentation. Newer, unreviewed wire versions are refused. The URL generator also single-quotes the numeric `TLIST` value, as documented by JPL. A matching header is **not** authentication of NASA/JPL.


## Safe rollback follow-up

The downloader now imports `rollback-horizons-directory.mjs` instead of calling recursive `rm` on an error. The rollback preflights the complete directory and tracks device/inode, size, modification time and change time for each file created by this run. If even one artifact differs or a foreign file is present, the tool retains the whole directory for manual review. See [HORIZONS_SAFE_ROLLBACK.md](HORIZONS_SAFE_ROLLBACK.md).

## D-14 — Unique pre-table Horizons header fields

The acquisition parser now imports the **shared** `strict-horizons-headers.mjs` reader. It extracts critical metadata only from the text preceding the first `$$SOE` vector-table marker. A missing field cannot be supplied by a line added after the vector table or in a response footer.

The following pre-table fields are required **exactly once** (case-insensitive labels): `API VERSION`, `API SOURCE`, `Target body name`, `Center body name`, `Center-site name`, `Output units`, `Output type`, `Output format`, `Reference frame`, coordinate system, and `Start time`. The documented `Coordinate systm` and `Coordinate system` spellings are **mutually exclusive aliases**. Duplicates, blank values and control characters result in fixed parser errors.

This helper is used by both the network downloader and the offline original-response verifier, so there is no separate, weaker interpretation of target/frame/center metadata. The API version and content are still self-asserted text; this is a structural guard, **not** cryptographic source authentication.

## D-16 — Descriptor-attested original files

The network downloader now uses `writeOwnedFileOnce` to exclusively create and write each raw response and the manifest **through a real file handle**, capturing inode and metadata from that descriptor before looking up the path and adding it to the rollback ownership list. The prior gap (file could be substituted after `writeFile` but before a pathname-only ownership capture) is narrowed. File name traversal, existing files, symlinks, changed directories, empty/oversized data or file/directory identity changes fail closed. The rollback leaves ambiguous partial directories untouched. See `docs/HORIZONS_SAFE_ROLLBACK.md`. The protection is best effort and does not eliminate hostile concurrent filesystem races.

**Tests executed:** 9 additional real-filesystem owned-write tests + 42 previously runnable isolated tests = **51/51 PASS** with Node.js 22.16.0. The full current feature suite now comprises **84** targeted cases, still not run as a whole in this partial checkout.
